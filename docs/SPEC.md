## 1. 題目定案

### 1.1 名稱

**正式名稱**
> 多路口 V2X 協同危險預警系統：基於 MEC 邊緣軟標籤交換的跨路口風險預測

**簡短名稱**：MEC 協同 V2X 危險預警

主標讓非專業評審三秒看懂；「軟標籤交換」是手段，放副標。

### 1.2 一句話定位

以路側單元（RSU）作為 MEC 邊緣節點，各路口在**不交換原始車輛軌跡**的前提下，透過公共代理資料集交換軟標籤（logits），協同訓練輕量級風險**預測**模型，並在 5G-MEC 平台上完成端到端實作與可驗證展示。

### 1.3 與平台範例的差異（務必在企劃書明確列出）

平台提供的範例 `KevinTseng-0430/SUMO-V2X-TTC` 已完成單路口 TTC 碰撞預警。所有參賽隊伍皆可取得。因此必須明確標示差異：

| 面向 | 平台範例 | 本作品 |
|---|---|---|
| 判斷方式 | 當下 TTC 門檻規則 | 序列模型預測未來 3 秒風險 |
| 時序性質 | 偵測（事件已發生） | 預測（事件發生前） |
| 場景 | 單路口、直線追撞 | 雙路口、含交叉衝突與異質車流 |
| MEC App 數量 | 1 | 2（透過 Service Registry 互相發現） |
| 節點間協作 | 無 | 聯邦蒸餾（logits 交換） |
| 比較基準 | MEC vs Cloud 延遲 | MEC vs Cloud 延遲 + 單獨訓練 vs 協同訓練 + 規則 vs 模型提前量 |

**規則基準線會被保留並實作**，作為對照組，不是被丟棄。

## 2. 核心論證鏈（企劃書的骨幹）

每一環都必須能獨立回答評審的「為什麼」。開發時若發現某一環站不住，必須回頭修正設計而非硬拗。

**Q1：為什麼需要預警？**
路口事故佔比高，3GPP TR 22.886 對安全相關 V2X 服務的端到端延遲要求嚴格（remote driving 情境列出 20 ms 級需求），集中式雲端處理難以滿足。

**Q2：為什麼規則不夠，需要學習模型？**
TTC 規則只能在衝突已經逼近時觸發，留給駕駛的反應時間有限；且 TTC 對非共線的交叉衝突定義不良。學習模型以過去 2 秒的運動序列預測未來 3 秒的最小 TTC/PET，可在規則觸發前先行示警。
→ **可量化**：平均提前預警時間（lead time）差異。

**Q3：為什麼需要跨路口協同？**
不同路口的幾何、號誌、車流組成不同，各自的危險事件型態分布偏斜（見 §4.3）。單一路口訓練出的模型遇到對方路口的型態會失效。
→ **可量化**：A 的模型在 B 的測試集上的 macro-F1。

**Q4：為什麼不直接把資料集中訓練？**
（a）上行頻寬：原始 BSM 為每車每 100 ms 一筆，持續上傳成本高；
（b）延遲：集中訓練後再下發模型，更新週期長；
（c）法規：台灣個資法對車輛軌跡的敏感度，集中式車路雲方案難以直接移植。

**Q5：為什麼用蒸餾而不用 FedAvg？**
（a）傳輸量：本專案模型約 4.84 萬參數（48,419 params ≈ 189 KB fp32），logits 交換為 2000 × 3 × 4 bytes ≈ 24 KB，約省 8.1 倍；
（b）模型異構：各路口可依算力採用不同模型結構，FedAvg 要求結構一致。
→ **可量化**：每輪傳輸 bytes 對比長條圖。

> **設計警示（已在規格中處理）**：若模型過小（例如兩層 MLP，約 1.4k 參數 ≈ 5.8 KB），FedAvg 的傳輸量反而低於 logits，論證會反轉。這是本專案採用序列模型而非簡單 MLP 的主要原因之一。開發過程中**不得**為了省事把模型換回極小 MLP。

**Q6：為什麼需要 MEC？**
（a）推論就近執行，端到端告警延遲遠低於雲端路徑（已有平台範例的 Cloud 對照可用）；
（b）logits 交換本身註冊為 MEC Service，透過 Discovery and Service Registry 與 MEP Gateway 完成節點互相發現與呼叫，符合 ETSI GS MEC 003 / 011 的平台能力定義；
（c）MEC App 維護每車的滑動視窗狀態，屬於有狀態邊緣服務，無法在無狀態雲端函式中低成本實現。

## 3. 系統架構

### 3.1 環境拓樸（沿用培訓營教材，不自創）

```
實體主機（32 GB RAM / 8 核 / Ubuntu）
├── VM1：free5GC + OAI-MEP + MEC Apps
│     NIC1 ens33  NAT        172.16.211.0/24
│     NIC2 ens36  Host-only  192.168.113.131
│     lo: 172.16.6.10（MEC App 綁定）、172.16.6.100（MEP Gateway 對外入口）
│     建議 8 GB RAM / 4 核 / 40 GB
└── VM2：UERANSIM + SUMO + UE Client
      NIC1 ens33  NAT        172.16.211.0/24
      NIC2 ens36  Host-only  192.168.113.132
      UE tun: uesimtun0 → 10.60.0.x
      建議 8 GB RAM / 4 核 / 40 GB
```

**前置確認（D1 第一件事）**
- `grep -cw vmx /proc/cpuinfo` 大於 0 且 `/dev/kvm` 存在 → 可開巢狀虛擬化，照上述雙 VM 建置。
- 若不可 → 退回單機部署，全部裝在同一台 Ubuntu 上，host-only 網段以 Linux bridge 或 veth pair 取代；教材中的 `iptables -t nat -I PREROUTING 1 -i upfgtp ...` 的 `-i` 介面名稱需對應調整。此變更**不影響題目與任何評估指標**，僅影響部署腳本。
- `lsmod | grep gtp` 為空時，需 `cd ~/gtp5g && make clean && make && sudo make install`。gtp5g 為 kernel module，需可編譯核心模組的環境。

### 3.2 資料流

```
SUMO（雙路口，TraCI 即時輸出）
  ↓ 車輛 id / 位置 / 速度 / 加速度 / 航向 / 車道 / 號誌相位
UE Client（sumo_ue_sender.py 改寫，封裝 V2X message，欄位參考 SAE J2735 BSM）
  ↓ HTTP POST，--interface uesimtun0
UERANSIM（UE / gNB）→ free5GC（N3 → UPF → N6）
  ↓
iptables DNAT（172.16.6.100:80 → Kong container:80）
  ↓
MEP Gateway / Kong（依路徑分流）
  ├── /mec/v2x/a → MEC App A（路口 A，172.16.6.10:5002）
  └── /mec/v2x/b → MEC App B（路口 B，172.16.6.10:5003）
        ├── 維護每車 20 步（2 秒）滑動視窗 ring buffer
        ├── 序列模型推論 → risk level {0,1,2}
        ├── 規則基準線同步計算（對照組）
        ├── 回傳告警給 UE
        └── 寫入結構化 log

聯邦蒸餾（獨立於即時推論的背景流程）
  MEC App A/B 各自向 Discovery and Service Registry 註冊 fd-service
  → 透過 MEP Gateway 互相取得對方對公共代理資料集的 logits
  → KL 蒸餾更新本地模型 → 熱替換推論權重
```

**關鍵設計**：FD 交換走 Kong 與 Service Registry，不走共享 volume。共享 volume 僅列為備援（見 §12）。這是「MEC 使用程度」這個子項目的主要得分點。

## 4. SUMO 場景規格

### 4.1 三個場景

| 場景 | 用途 | 說明 |
|---|---|---|
| `intersection_a` | 路口 A 訓練 + 即時展示 | 號誌化四叉路口 |
| `intersection_b` | 路口 B 訓練 + 即時展示 | 無號誌 T 字路口 |
| `proxy_public` | 公共代理資料集 | 中性幾何，僅用於產生 logits，不含標籤，兩端持有相同副本 |

### 4.2 共同設定

- SUMO 版本：1.27.0（教材環境已有，勿升級）
- step-length：0.1 s
- 取樣：每車每 0.1 s 一筆狀態
- 啟用 SSM device 輸出 TTC、PET、DRAC：
  ```xml
  <param key="device.ssm.measures" value="TTC PET DRAC"/>
  <param key="device.ssm.thresholds" value="3.0 2.0 3.0"/>
  <param key="device.ssm.trajectories" value="true"/>
  ```
  （v1.4）實作上以 sumocfg 的 `<ssm_device>` 區段設定（效果相同），輸出檔為 `ssm.xml.gz`。
  `trajectories=true` 的逐步 TTC 會被用於標籤（見 §5.4 的補充）。
- 為確保危險樣本足量，調整駕駛參數：`sigma`（imperfection）0.5–0.8、`tau` 0.5–0.8、部分車輛 `speedFactor` 上調。SUMO 預設的 Krauss 模型近乎無碰撞，不調整將產生極少正樣本。
- 每個場景產生至少 3600 秒模擬資料供訓練。

### 4.3 異質性設計（本專案成敗關鍵）

**兩個路口的危險事件型態必須刻意不同**，否則聯邦蒸餾不會有可觀測的增益，§2 的 Q3 論證將無法驗證。

| 項目 | 路口 A | 路口 B |
|---|---|---|
| 幾何 | 號誌化四叉，雙向各 2 車道 | 無號誌 T 字匯入，單車道 |
| 號誌 | 有，週期 60 s | 無，僅停讓標線 |
| 車流組成 | 小客車 90%、大車 10% | 小客車 60%、機車 40% |
| 流量 | 高（1200 veh/h/方向） | 中（500 veh/h/方向） |
| 主要衝突型態 | 追撞、對向左轉穿越 | 側向匯入、機車鑽行 |
| 危險樣本類別分布 | 追撞為主，側撞樣本 < 5% | 側撞為主，追撞樣本 < 10% |

**驗證方式**：D6 完成場景後，先各自統計危險樣本的衝突型態分布，確認兩者明顯偏斜。若分布相近，必須回頭調參，**不可直接進入 §7 的蒸餾階段**。

## 5. 資料格式與標籤定義

### 5.1 V2X 上行訊息（UE → MEC）

JSON，欄位命名參考 SAE J2735 BSM：

```json
{
  "msg_id": "uuid4",
  "ts_ue": 1758240000.123,
  "intersection": "A",
  "vehicle_id": "veh_0042",
  "position": {"x": 120.4, "y": 88.1},
  "speed": 12.3,
  "accel": -1.2,
  "heading": 87.5,
  "lane_id": "e1_0",
  "signal_phase": "G",
  "sim_time": 305.4,
  "length": 4.5
}
```

`ts_ue` 為 UE 端送出時間戳，供延遲量測用。
`length` 為車長（公尺，對應 J2735 BSM 的 VehicleSize），規則基準線算保險桿間距用（§6.3）；未帶時預設 5.0，與平台範例相同。

### 5.2 特徵向量（每時間步 8 維）

MEC App 端根據收到的 BSM 與自身維護的鄰車表計算，**不由 UE 端計算**（降低上行負載，並讓 MEC 的運算角色明確）。

| # | 特徵 | 說明 |
|---|---|---|
| 1 | `ego_speed` | 自車速度 m/s |
| 2 | `ego_accel` | 自車加速度 m/s² |
| 3 | `rel_dist` | 與最近衝突車輛的距離 m |
| 4 | `rel_speed` | 相對速度 m/s（接近為正） |
| 5 | `heading_diff` | 航向夾角，正規化至 [-1, 1] |
| 6 | `same_lane` | 是否同車道 {0, 1} |
| 7 | `dist_to_stopline` | 距停止線距離 m |
| 8 | `signal_state` | 號誌狀態 {0 紅, 0.5 黃, 1 綠}；無號誌路口固定 1 |

所有特徵以固定 min-max 範圍正規化至 [0, 1]，正規化參數寫死在設定檔並兩端共用，**不可各自用自己的資料統計**（否則 logits 不可比）。

### 5.3 模型輸入

過去 2 秒滑動視窗，20 個時間步 × 8 維 → shape `(20, 8)`。

MEC App 為每台車維護一個 `deque(maxlen=20)`。車輛首次出現且不足 20 步時，以第一筆狀態向前填充。

### 5.4 標籤定義（三級分類）

以該車**未來 3 秒內**（即未來 30 個時間步）與任一其他車輛之間的**最小 TTC 或 PET** 決定：

| 標籤 | 類別 | 條件 |
|---|---|---|
| 2 | 危險 | min(TTC, PET) < 1.5 s |
| 1 | 注意 | 1.5 s ≤ min(TTC, PET) < 3.0 s |
| 0 | 安全 | 其他 |

標籤由 SUMO SSM device 的輸出離線計算，僅用於訓練與評估，即時推論時不可取得。

（v1.4 補充）「未來 3 秒內的最小 TTC」取自 SSM 的**逐步 TTC**（`TTCSpan`，每 0.1 秒一值），
而非每個衝突只記一次的 `minTTC`。後者會漏標：某衝突的最小值若發生在 t 之前、
但 t 之後的 3 秒內 TTC 仍偏低，只看 minTTC 會把 t 錯標為安全（`tests/test_build_dataset.py` 有構造此反例）。
PET 本質上每個衝突只有一個值，照舊取單點。

**這是本專案的核心設計**：特徵取自過去與當下，標籤取自未來 → 這是預測任務，規則基準線在原理上做不到。

## 6. 模型規格

### 6.1 結構（1D-CNN）

```
Input (20, 8)
 → Conv1d(8→32, kernel=3, padding=1) + ReLU + BatchNorm
 → Conv1d(32→64, kernel=3, padding=1) + ReLU + BatchNorm
 → MaxPool1d(2)            # (64, 10)
 → Flatten                 # 640
 → Linear(640→64) + ReLU + Dropout(0.3)
 → Linear(64→3)
 → (訓練時 softmax with temperature T)
```

參數量 48,419，fp32 約 189 KB（已以 PyTorch 實測確認）。CPU 推論時間預期 < 1 ms。

**不得為了簡化改用兩層 MLP**，原因見 §2 Q5 的設計警示。

### 6.2 訓練設定

- 損失：交叉熵，類別權重以 inverse frequency 補償不平衡
- 優化器：Adam，lr 1e-3
- Batch size：256
- Epochs：本地預訓練 30，每輪蒸餾後 5
- 資料切分：每個路口 70/15/15（train/val/test），**依時間切分不隨機切**，避免同一事件的相鄰時間步同時出現在訓練與測試集

### 6.3 規則基準線（對照組，必須實作）

沿用平台範例的邏輯：當下 TTC < 1.5 s 即發出危險告警、< 3.0 s 發出注意告警。用於計算提前預警時間差。

TTC 的算法與平台範例（`compute_rear_end_ttc`）逐條一致：

- 只看**同車道、自車前方最近的一台車**（追撞）
- 間距 = 兩車頭距離 − 前車車長（保險桿到保險桿）；間距 ≤ 0 視為已碰撞，TTC = 0
- TTC = 間距 ÷（自車速度 − 前車速度）；相對速度 ≤ 0.1 m/s 視為沒有在接近

門檻不用平台範例的預設值（4.0 / 5.0 s），改用與模型標籤相同的 1.5 / 3.0 s，兩者才在同一把尺上比較。
實作：`mec_app/rule_baseline.py` 的 `evaluate_platform`；MEC App 與 `training/lead_time.py` 共用。

### 6.4 兩段式警示（v1.4 新增）

設計目標：**幾乎抓到全部危險，同時讓強烈警報可信**。只追求不漏報的話，「永遠都喊危險」就能做到零漏報，
但駕駛很快會忽略警告（alarm fatigue），等於沒有預警；這也是真實前方碰撞警示（FCW）採兩段式的原因。

模型輸出「未來 3 秒內發生危險的機率」p，同一個分數、兩條線：

| 等級 | 呈現方式（展示時） | 門檻怎麼定 | 負責的事 |
|---|---|---|---|
| 注意 | 溫和提示（面板圖示） | 事件召回率 ≥ 95% 的最高門檻 | 幾乎全抓到 |
| 危險 | 強烈警報（聲音） | 警示精準度 ≥ 50% 的最低門檻（不低於注意） | 喊了要準 |

評估單位（`training/events.py`）：

- **事件**：一對車 min(TTC, PET) 首次 < 1.5 s；事件前 3 秒到事件後 0.5 秒內，雙方任一台**有被提醒**就算抓到。
  不要求警示指向對方那台車，因為模型的標籤就是「這台車未來 3 秒會不會遇到危險（不論對象）」，駕駛收到提醒就會減速注意。
  （§8.1「比規則早幾秒」仍用指向對方的嚴格比法。）
- **一次警示**：同一台車間隔 < 1 秒的連續警示算一次（駕駛感受到的是一次提醒）。
- **誤報**：注意等級的警示之後 3.5 秒內沒出現 TTC < 3 s；危險等級的警示之後沒出現 TTC < 1.5 s。
  以「**每次通過路口平均被誤報幾次**」表示。
- 門檻只用**本路口驗證資料**校準，每產生一版權重（round 0、每一輪蒸餾後）就校準一次，
  存於 `models/{node}/thresholds.json`；MEC App 載入哪一版權重就用它的兩條門檻。
- 參數（95%、50%）在 `config.yaml` 的 `decision` 區。

## 7. 聯邦蒸餾協定

### 7.1 公共代理資料集

- 由 `proxy_public` 場景產生，固定 2000 筆樣本，shape `(2000, 20, 8)`
- 僅含特徵，**不含標籤**
- 產生後存為 `proxy_set.npy`，兩端持有位元完全相同的副本，檔案 SHA256 寫入 log 供佐證
- 樣本需涵蓋三類風險的分布（透過對 proxy 場景的 SSM 結果做分層抽樣，但抽樣後即丟棄標籤）

### 7.2 交換介面

註冊至 Discovery and Service Registry 後，經 MEP Gateway 呼叫。

**GET** `/mec/fd/{node}/logits?round={n}`

回應：
```json
{
  "node_id": "A",
  "round": 3,
  "proxy_hash": "sha256:...",
  "temperature": 3.0,
  "n_samples": 2000,
  "n_classes": 3,
  "encoding": "float32-base64",
  "logits": "<base64>",
  "bytes": 24000,
  "ts": 1758240000.123
}
```

**GET** `/mec/fd/{node}/status` → 回傳目前輪數、是否就緒、上一輪的本地驗證分數。

呼叫方需驗證 `proxy_hash` 與自身一致，不一致則拒絕該輪並記錄錯誤。

**輪次對齊**：`round = n ≥ 1` 回傳該節點第 n 輪「發布」的軟標籤（§7.4 步驟 2 產生後即發布）；
尚未發布回 **409**，呼叫方每 3 秒重試，最多等 30 分鐘。`round = 0` 以目前模型即時計算。
兩節點每輪耗時不同（A 的資料量約為 B 的 4 倍），不對齊的話較快的一方會一直拿到對方上一輪甚至第 0 輪的結果。

節點間的呼叫由 VM1 本機發出，不經 `upfgtp`，所以 VM1 的 OUTPUT 鏈另有一條 DNAT
（`deploy/setup_vm1.sh` 步驟 6），讓它同樣經過 MEP Gateway。

### 7.3 蒸餾損失

```
L = (1 - α) · CE(y_true, p_local) + α · T² · KL(p_peer_soft ‖ p_local_soft)
```

- α：**非對稱**，A = 0.5、B = 0（v1.4 依調參結果修訂，原為兩端 0.5）
- T = 3.0
- 協同各輪的學習率 1e-4（預訓練為 1e-3；微調用較小學習率，實測分數較不跳動）
- `p_peer_soft` 為對方在溫度 T 下的軟標籤
- `T²` 係數用於平衡軟硬標籤的梯度量級（Hinton et al. 標準做法）

**參數怎麼來的**（`training/tune_fd.py`，只用驗證資料，測試資料不碰）：

- 選擇準則用實務語言定義：成本 = R × 漏報 + 誤報（每 1000 筆），R = 漏報一次抵幾次誤報，預設 10，
  並檢查 R = 3 / 10 / 30 的結論是否一致
- 搜尋範圍刻意很小：α ∈ {0, 0.1, 0.3, 0.5} × 每輪學習率 ∈ {1e-3, 1e-4}，另試「公共資料改為自然比例」與「非對稱 α」。
  α = 0 即「不協同、只多訓練同樣次數」的對照組
- 結果：兩端都協同時，A 的模型用在 B 路口成本下降（A 學到 B 的側向衝突），但 B 的模型用在 A 路口成本大增（誤報暴增）；
  逐節點套用同一準則得到「A 吸收、B 只提供」，在 3 個亂數種子下都是成本最低的設定
- **效益要照實講**：A 的模型用在 B 路口的成本，比不協同低約 4%（R = 10）到 11%（R = 3），3 個種子方向一致；
  漏報極貴（R = 30）時沒有穩定差異
- 真實情境的包裝：每個路口的邊緣節點可以自主決定是否採用協同更新；B 仍把軟標籤提供給 A

**危險警告門檻**（`training/decision.py`）：模型認為危險的機率 ≥ τ 才喊危險。每產生一版權重（round 0、每一輪），
就用本路口驗證資料找出成本最低的 τ，存於 `models/{node}/thresholds.json`；MEC App 載入哪一版權重就用它的門檻。
對應真實部署「新模型上線前先做本地校準」。

### 7.4 回合流程

```
for round in 1..5:
    1. 本地以 train set 訓練 5 epochs
    2. 對 proxy_set 前向，產生溫度 T 的軟標籤
    3. 向 Service Registry 查詢對方 fd-service 位址
    4. 經 MEP Gateway GET 對方 logits，驗證 proxy_hash
    5. 以 §7.3 損失更新本地模型 5 epochs
    6. 在本地 val set 與對方 test set 上評估，寫入 log
    7. 記錄本輪傳輸 bytes
```

第 0 輪（僅本地預訓練 30 epochs，無交換）即為「單獨訓練」基準，必須完整保留其模型與評估結果。

實作注意（v1.4 實測後補上）：

- **代理資料前向時凍結 BatchNorm 統計**（`distill.frozen_bn_stats`）。代理資料來自中性路口，若讓它更新 BN 的 running mean/var，
  推論時用的是混合統計，本地表現整個崩掉（A 本地 val macro-F1 0.75 → 0.46，與 α、代理抽樣數皆無關）。梯度照常回傳。
- 兩節點在同一台 4 核 VM1 上同時蒸餾時，各限 2 條運算執行緒（`train.distill_threads`）；不限的話互搶，一輪從約 1 分鐘變成 29 分鐘。
- 步驟 7 的線上傳輸量以 base64 字串長度計（約 32,000 B），原始張量 24,000 B 另記於 `bytes_sent`。

### 7.5 模型熱替換

蒸餾完成後，推論 App 從 `models/{node}/current.pt` 重新載入權重。以原子性 rename 避免載入到寫到一半的檔案。展示時可即時切換 `round_0`（單獨）與 `round_5`（協同）兩組權重，這是現場 demo 的關鍵互動。

## 8. 量測與評估

### 8.1 主指標

| 指標 | 定義 | 為何重要 |
|---|---|---|
| **跨路口 macro-F1** | A 的模型在 B 的 test set 上，反之亦然 | 驗證 §2 Q3，主要成果指標 |
| **平均提前預警時間** | 對同一危險事件，模型首次示警與規則首次示警的時間差 | 驗證 §2 Q2，最直觀的價值 |
| **每輪傳輸 bytes** | logits vs 模型參數 | 驗證 §2 Q5 |
| **MEC vs Cloud E2E 延遲** | 沿用平台範例的對照做法 | 驗證 §2 Q6 |

次要指標：本地 macro-F1、各類別 recall（危險類 recall 最重要）、不同車流密度下的表現變化、告警成功率。

「同一危險事件」的界定（實作：`training/lead_time.py`）：

- 一件事件 = SSM 記到的**一對車** min(TTC, PET) 首次 < 1.5 s；同一對 5 秒內的連續危險算同一件
- 雙方任一台收到**指向對方**的警告即算有預警（模型看回應的 `conflict_with`，規則看 `rule_target`）。
  追撞時規則只提醒後車，所以不能要求兩台都收到；車隊中每台車都可能正被提醒注意自己的前車，那是別的危險，所以要看對象
- 只看事件前 3 秒（模型的預測範圍）到事件後 0.5 秒（讓規則有機會當下觸發），故提早時間上限約 3 秒
- 與提早秒數一起報：規則漏掉而模型抓到的件數，以及模型喊危險的準確率（避免「一直喊」得到漂亮的提早秒數）

### 8.2 延遲拆解點位

所有時間戳在 **同一台實體主機** 上取得，避免時鐘同步爭議；此限制需在報告中主動說明。

| 區段 | 起點 | 終點 |
|---|---|---|
| T1 上行網路 | UE 送出 `ts_ue` | MEC App 收到請求 |
| T2 特徵組裝 | 收到請求 | 滑動視窗就緒 |
| T3 模型推論 | 視窗就緒 | 輸出 risk level |
| T4 下行回傳 | 產生回應 | UE 收到 |
| T_total | `ts_ue` | UE 收到 |

### 8.3 三張核心圖表

1. **收斂曲線**：x 軸為蒸餾輪數 0–5，y 軸為跨路口 macro-F1，兩條線（A→B、B→A），對照水平虛線為單獨訓練。
2. **傳輸量對比**：長條圖，logits（原始張量 24,000 B；base64 上線約 32 KB）vs 模型參數（189 KB），對數軸，標註倍數。圖與內文須標明採用的是原始張量大小或 HTTP 實際傳輸量，兩者不可混用。
3. **延遲拆解堆疊圖**：T1–T4 分段，MEC 路徑與 Cloud 路徑並列。

第三張可直接沿用平台範例已有的 MEC / Cloud 對照做法，成本最低、說服力高。

### 8.4 Log 規格

所有 log 為 JSON Lines，每行一筆，欄位固定：

- `logs/inference_{node}.jsonl`：msg_id, ts_ue, ts_recv, ts_infer_done, ts_resp, vehicle_id, risk_pred, risk_rule, ttc_now
- `logs/fd_rounds.jsonl`：round, node, bytes_sent, local_f1, cross_f1, duration_s
- `logs/events.jsonl`：event_id, intersection, first_warn_model_t, first_warn_rule_t, label_t, lead_time

畫圖腳本只讀這三個檔，不得從程式內部直接產圖，確保可重現性。

## 13. 決賽擴充（11/02 入圍後至 12/12）

### 13.4 現場環境
- 自備旅行路由器，全部裝置設靜態 IP，整套離線可跑。會場 WiFi 不可信。
- `deploy/run_all.sh` 必須能在 10 分鐘內從冷開機還原至可展示狀態，並在 12/11 場布時完整演練一次。

## 15. 給 Claude Code 的指示

1. **本文件為唯一事實來源。** 實作前先讀完本文件；若發現規格內部矛盾或技術上不可行，先提出並等待確認，不要自行改設計。
2. **優先順序**：先讓系統能跑（D1–D9），再讓成果變好（D10–D14）。任何時間點都必須有一個可展示的狀態。
3. **不得簡化的項目**：序列模型不可換成小 MLP（§2 Q5）；標籤必須用未來視窗（§5.4）；FD 交換必須走 Kong（§3.2）。這三項是題目成立的基礎。
4. **log 先於功能**：任何新模組先把 §8.4 的 log 欄位寫好再寫邏輯。實驗數據是初賽第 6 項繳交要求。
5. **正規化參數兩端共用**，寫在 `config.yaml`，不得各自計算。
6. **所有部署動作寫成 `deploy/` 下的腳本**，不接受「我在終端機下過了」。
7. **環境自建原則（v1.3 修訂）。** 本專案**不依賴培訓營提供的 VM 映像檔**，
   所有元件由 `deploy/` 下的腳本從上游原始碼自行建置，版本鎖定於
   `deploy/versions.env`。理由：
   （a）決賽須繳交完整程式碼供評審辨識原創性，「能從零重現」本身就是證據；
   （b）環境壞掉時可一行指令重建，不必等別人給映像檔；
   （c）本專案的情境是**雙 MEC 節點 + 聯邦蒸餾**，教材的單一 App 示範不涵蓋，
   設定本來就必須自己寫。

   **但元件本身仍採用競賽平台指定的上游專案**：free5GC、UERANSIM、OAI-MEP。
   這條界線不可跨越——初賽評分「系統架構完整性（含競賽平台關聯性）」佔 40%，
   且 §2 Q6 的 MEC 論證建立在 ETSI MEC 003/011 的 Service Registry 與
   MEP Gateway 之上，那是 OAI-MEP 提供的平台能力。自行實作 MEP 會同時
   打掉這 40% 與 Q6 的立論基礎。

   教材中的**設定值與指令仍是主要參考**（Kong Service/Route 建立、DNAT 規則、
   N6 位址、網段配置），因為那是平台團隊驗證過的組合；`docs/platform-notes.md`
   逐條抄錄並標註頁次。差別在於「我們知道每一行在做什麼，而且能重建它」，
   而不是「照著貼」。
